# Диагностика, diff/backup и разбор проблем

## Проверка по слоям

| Слой | Что проверить | Чего это ещё не доказывает |
|---|---|---|
| DNS/TCP | Proxy hostname разрешается; порт доступен | TLS, пароль, API |
| TLS до HTTPS-прокси | Валидный сертификат, правильный hostname | CONNECT и API |
| Proxy auth / CONNECT | `http_connect=200` | Доступность модели/аккаунта |
| TLS конечного сайта | `ssl_verify_result=0` при состоявшемся соединении | Регион/подписка/streaming |
| HTTP API | `401` без API-ключа с ответом нужного сервиса | Генерация и браузерный вход |
| Живой клиент | Активная конфигурация, новый процесс, реальные TCP-соединения | Все дополнительные endpoints |
| Функциональная проверка | Открытие приложения, авторизация, ответ модели/stream | Будущую устойчивость или все инструменты |

Нули `TLS verification` при `HTTP=000` и ошибке DNS не означают успешный TLS: соединения не было. Всегда интерпретировать вместе exit code, CONNECT и HTTP.

## Независимый сетевой тест

Использовать `scripts/probe_proxy.py` из навыка или curl с явным proxy. Для HTTPS upstream смотреть:

```text
HTTP status
Proxy CONNECT status
TLS verification
Proxy TLS verification
```

Проверять `https://api.anthropic.com/v1/models` с `anthropic-version: 2023-06-01` или `https://api.openai.com/v1/models`, не передавая API key. Для проверки авторизации провайдера использовать отдельно разрешённый реальный клиент.

Изолировать тест от `https_proxy`/`HTTPS_PROXY`, `http_proxy`/`HTTP_PROXY`, `all_proxy`/`ALL_PROXY` и обоих `NO_PROXY`; поставить явный `--noproxy ''`, когда нужно обязательно проверить маршрут. Не выводить секрет в argv: передавать конфиг curl через stdin либо использовать существующий защищённый источник. Не снимать verbose-трассы с auth без редактирования.

Коды:

- curl `5`: не разрешается proxy hostname; проверить сеть и sandbox, не объявлять пароль неверным.
- curl `7`: TCP connection refused/unreachable; для нового LaunchAgent дождаться bind.
- `407`: upstream требует/отклоняет proxy auth.
- `CONNECT 200` и конечный `401`: туннель и API достижимы; нет API-ключа.
- `403`: изучить безопасный фрагмент ответа. Region error, Cloudflare и API permission error — разные причины.
- Загрузка UI работает, streaming ломается: исследовать WebSocket/длительность потока/авторизацию; не менять base URL наугад.

## Diff и backup

Показать только релевантный diff, подменив реальные credentials маркером. На исполнении использовать реальные значения, а не маркер. Существующие файлы не переформатировать без необходимости; сохранять неизвестные поля, комментарии и профиль пользователя.

Перед перезаписью:

1. Прочитать исходные bytes, mode и при необходимости symlink target; не заменять symlink неожиданно.
2. Создать уникальный backup с датой/временем и понятным назначением. Для macOS исходного случая время показывалось в `Asia/Baghdad`.
3. Скопировать с метаданными (`shutil.copy2`) и проверить `backup.read_bytes() == original`.
4. Проверить, что исходник не изменился с момента diff. При изменении повторить чтение/merge.
5. Сохранить подготовленный файл с правами `0600` для секретов. Для файлов, которые приложение может писать одновременно, предпочесть корректную остановку либо атомарную замену после проверки текущего состояния.
6. Повторно разобрать JSON/TOML/plist и проверить требуемые значения без печати пароля.

Для новых файлов backup не существует: в манифесте явно записать «ранее отсутствовал». Не создавать фиктивную пустую копию. Для установленной службы записать label, бинарник, конфиг, log path и способ unload. Не удалять резервные копии до подтверждения результата.

Если приложение активно сохраняет `config.json`, snapshot во время записи может измениться; перепроверить байты или завершить приложение корректно и повторить копирование. Не считать сам факт существования backup доказательством пригодности.

## Проблемы исходной дискуссии

### 1. Sandbox выдавал DNS-ошибку

Первый curl получил `Could not resolve proxy: vpn.anatolix.net`. Повтор с разрешённым доступом вне sandbox вернул CONNECT `200` и API `401`. Это была проблема среды исполнения теста, а не доказанная неисправность proxy.

На новой машине соблюдать текущие permissions: если требуется escalation, запросить штатным механизмом; не обходить ограничение другим инструментом. Позже в исходной среде sandbox был отключён пользователем — это не инструкция выключать его при повторении.

### 2. Смешались названия продуктов

«Локально Claude» сначала могло означать CLI или Desktop. Обнаружены оба; пользователь уточнил Desktop. Позже сообщение «codex говорит Claude isn't available…» оказалось про окно Claude Desktop. Проверка журналов установила источник. Нужно спросить об окне/команде и параллельно читать релевантные логи, а не настраивать не тот продукт.

### 3. Успешный VS Code не исправил Desktop

Были настроены `claudeCode.environmentVariables` и затем `~/.claude/settings.json`. Пользователь подтвердил VS Code, но Desktop продолжал выдавать region error. В `main.log` был `proxy for https://claude.ai resolved … (direct)`, системный proxy отсутствовал. Конфиг агента не маршрутизировал веб-приложение.

### 4. Утверждение о Desktop было слишком широким

Нельзя говорить «Claude не умеет пароль на прокси». Claude Code умеет, в том числе его движок внутри Desktop. Ограничение embedded credentials относится к `egressProxyUrl` самого Desktop и его интерактивной proxy-авторизации. После уточнения выбран local forwarder, как предлагает Anthropic.

### 5. Пример хаба был частично недоступен

Сохранённый HTML был оболочкой ~1,3 КБ с пустым `#app` и ссылкой на hydrate.js; текста инструкции в нём не было. Не выдумывать её содержимое. PDF содержал одну страницу, но правые части длинного JSON были обрезаны и визуально, и при extraction. Удалось установить назначение полей, но не полные секреты/URL. Не восстанавливать обрезанные значения догадкой.

### 6. API-шлюз был ошибочно похож на обычный proxy

CoreInfra объединял network proxy с `ANTHROPIC_BASE_URL`, custom header и аналитикой inference. Для пользовательского CONNECT-прокси base URL/custom header не нужны. Документ не разрешал подключение аккаунта к стороннему сервису.

### 7. Наследование окружения могло подменить тест

У самого диагностического Codex уже были proxy env для пользователя `codex`. Claude требовался пользователь `claude`. Проверки из shell без явного источника могли тестировать чужую конфигурацию. Введение разных клиентов не даёт права смешивать их credentials.

### 8. Версии и схемы различались

CLI Claude был `2.1.92`, VS Code extension `2.1.288`, Desktop `2.19675.0`. Возможности проверялись по установленному `package.json`, bundled schema/loader и документации. Не выбирать поведение по версии соседнего клиента. Чтение `app.asar` было диагностикой; приложение не модифицировалось.

### 9. Угаданные URL документации возвращали 404

Часть страниц GOST и предполагаемых путей исходников отсутствовала; схему нашли в `go-gost/x/config/config.go`, официальный бинарник — через release API. Не устанавливать неподтверждённый пакет только потому, что одна документационная ссылка не открылась.

### 10. `running` не означал готовность listener

Сразу после `launchctl bootstrap` curl получил connection refused. Через короткое время localhost listener поднялся, тест прошёл. Требуется ограниченное ожидание bind и лог при сбое; не бесконечный retry.

### 11. Старые логи и preconnect могли дать неверный вывод

При shutdown старый Desktop дописал region errors. Затем новый процесс включил pinned proxy. Даже после marker встречался ранний `(direct)` preconnect; actual TCP connections, успешный load и свежие API-запросы подтвердили proxy. Нужно связать timestamp/process/phase и не считать весь исторический лог результатом нового запуска.

### 12. Краткий HTTP failure и Turnstile восстановились

После старта один load failure, затем запись `recovered after 1 failed attempt(s)` и загрузка claude.ai. Не объявлять неудачу до завершения штатного восстановления. Не обещать, что всякая CAPTCHA разрешится сама; если требуется действие, передать человеку.

### 13. Computer Use оказался недоступен

Попытка `cua.getApp("Claude")` вернула `Sky Computer Use service startup request failed`. Визуального подтверждения нет. Проверили startup marker, логи и TCP. В отчёте нельзя писать «я увидел рабочий чат» или «модель ответила».

### 14. Codex HTTP-profile найден, но его необходимость не доказана

На этапе создания навыка обнаружены `.env`, backup-манифест и `chatgpt-http` с `supports_websockets=false`. В видимой дискуссии не было причинно проверенного WebSocket-сбоя Codex. Зафиксировать профиль как состояние этой машины, а не обязательный шаг для всех.

## Когда остановиться

- После успешных нужных проверок не менять модели, провайдеров, sandbox или системный proxy ради дополнительной «надёжности».
- При managed policy conflict, неизвестном формате config, требуемой CAPTCHA или недоступном инструменте назвать конкретный предел и сохранить готовую часть работы.
- После неудачной попытки с реальным риском поломки вернуть прежний маршрут, не оставлять Desktop указывающим на остановленную службу.

## Формат отчёта

Коротко: клиенты и файлы, путь к backup, факт restart/service, подтверждённый маршрут, ошибки после изменения, проверялась ли генерация. Если не проверялась — прямо сказать. Не публиковать пароль или содержимое token cache.
